# Flight Haptic Controller

For the current staged workflow, start with the [Stage 3 peripheral checks
guide](docs/stage-3/README.md). Stage 2's clean build and user-reported Wokwi
execution are confirmed. Stage 3 adds signal-recording probes; its runtime checks
are pending. Sensor initialization still fails at the wake-register write.
The application below predates this fresh staged workflow and is not a newly
written minimal baseline.

STM32C031C6 firmware for the ENGE X200 Assignment 2 Wokwi circuit. The controller
reads MPU6050 acceleration at 50 Hz, calculates roll, pitch and unified tilt, and
drives the three servos through finite state machines with 5 degree inward
hysteresis. PA2 indicates autopilot; PB11 indicates manual mode. PA12 is a
debounced, edge-triggered mode button. Both clamped axes latch autopilot;
returning to manual requires a new press while both axes are free.

Download `downloads/FlightHapticController-project.zip` for the source and a
compiled firmware image that can be opened directly with Wokwi in VS Code.
This is an instrumented diagnostic build, not a verified fix for the reported
Wokwi startup failure. Rebuild after editing the source; simulator validation is
still required.

## Build and test

On Debian 13 in this cloud workspace:

```sh
bash scripts/setup-toolchain.sh
make -j4
make test
```

The setup script installs ARM GCC 14.2.1, binutils and newlib under
`/workspace/toolchains`, using signed Debian package indexes. It requires network
access to `deb.debian.org`, Debian archive keyrings, APT and `dpkg-deb`. Existing
cloud proxy and TLS trust settings are preserved. A prepared cloud snapshot
can retain these tools; rerun setup when they are missing or to refresh them.

With a system ARM GNU toolchain and newlib installed elsewhere, use
`make TOOLCHAIN_PATH= CROSS=arm-none-eabi-`. On Windows, install GNU Make and an
ARM GNU toolchain with newlib, then run that command in a compatible shell.
Host tests additionally require Bash and a native C compiler (`cc`).

The portable Makefile uses the actual repository linker script and recompiles
the sources into `build/`. It does not reuse the historical Windows-specific
`Debug/` objects. GCC 14.2.1 is used here rather than the STM32CubeIDE 14.3.1
toolchain named in the generated files. Optional CubeIDE cyclomatic-complexity
reports are not generated by this build.

## VS Code and Wokwi

1. Open this repository folder in VS Code and install the Wokwi extension.
2. Build with **Terminal → Run Build Task** or `make -j4`.
3. Run **Wokwi: Start Simulator**. `wokwi.toml` points at the new
   `build/FlightHapticController.elf`.
4. Use the accelerometer triples and transition sequences in
   [the validation guide](docs/assignment-validation.md). Record actual observed
   behavior for the report/video; predicted values are not simulator evidence.

The extension may require a Wokwi account/license. Simulation and the results
video must be checked in Wokwi; host tests cannot verify the simulator's I2C,
servo calibration, rotation direction or actual timing. The diagram's name and
student ID remain placeholders until supplied.

Servo commands use the Arduino Servo pulse range of 544–2400 microseconds.
Positive axis angles command `90 - angle`; negative angles therefore rotate
towards 180 degrees. Wokwi's public servo renderer increases its angle clockwise,
so this gives the required clockwise-negative convention. Confirm orientation
and calibration in the supplied circuit while recording. Physical servos may
require different calibration.

## Source layout and assumptions

- `Core/Src/main.c`: all application implementation: angle calculations, FSMs,
  I2C and GPIO fallback, scheduling, button debounce, PWM/LED output and USART1
  diagnostics, alongside the generated peripheral setup.
- `Core/Inc/main.h`: application types, numeric diagnostic enums and declarations.
- `Core/Startup/`, the remaining generated `Core/Src/` support files, `Drivers/`
  and the linker script: required STM32 startup, interrupt, CMSIS and HAL support.
  Keep these files when building or submitting; the two application files do not
  form a standalone firmware project.
- `tests/`: native regression checks; run with `make test`.
- `docs/assignment-validation.md`: FSM diagrams, boundary decisions and 1 g
  demonstration vectors.

Host tests select sections of the same `main.c` implementation. The Makefile
size-optimizes `main.c` and the HAL I2C driver to keep both measured read paths
and the fault trace within the MCU's 32 KB flash.

Exact 50 degree axis magnitudes enter clamping and exact 20 degree tilt enters
compliance, resolving equality gaps in the brief. Autopilot changes the mode
indicator and remains latched, while haptic feedback continues: the assignment
does not define aircraft stabilization dynamics. Sensor faults latch autopilot
and command neutral servos until valid measurements resume; manual mode then
requires a fresh safe button press. This is an educational simulation, not an
aircraft autopilot implementation.

STM32 startup, CMSIS and HAL code retain their existing vendor notices. New
controller, integration, tests and documentation were AI-assisted; they are not
attributed to lecture material or to the student. This repository does not
contain an observed-results video or a completed personal report.

## If the green LED flashes once and only red stays on

The initial green indication appears before sensor initialization finishes.
Red can indicate either a sensor fault or a healthy, latched autopilot mode.
Open the **Wokwi Terminal** and read the status messages from USART1 on PA9.
At level (`X=0, Y=0, Z=1`), `IMU=OK` with `mode=AUTO` requires a fresh blue-button
press to restore manual. `IMU=FAULT` blocks manual release.

The connected log reaches the RXNE wait after the register-address write, but
no byte arrives; its I2C `CR2` register still shows write direction. With the
sensor's SCL/SDA wires removed, the controller instead fails during the initial
write. This demonstrates that the sensor connection changes the hardware result,
while GPIO input reads report low in both circuits. The low GPIO readings alone
do not establish that the sensor physically holds either line down.

For exactly the measured RXNE timeout with TC set and read direction absent,
the current firmware resets I2C and tries a register-pointer write with STOP,
followed by a new read START. It selects this path only if it receives a real
sensor byte; writes still use the normal memory API. If it fails, the existing
GPIO fallback remains available. In a fault record, `SOFT split` identifies the
last attempted step: `0` unused, `1` I2C reset, `2` pointer write, `3` data read,
`4` success. `serr` is that step's HAL error. A healthy `IMU=OK` record with
`bus=HW hwerr=0x00000020` would show the alternative path recovered the sensor.
This has not yet been observed in Wokwi.

For a controlled comparison, `downloads/FlightHapticController-isolated-bus-test.zip`
contains the same compiled firmware with only the MPU6050's SCL and SDA wires
disconnected in `diagram.json`; both 4.7 kΩ pull-ups remain on PB8/PB9. Extract
it into a separate folder and run Wokwi, then compare `PINS BOOT` and `SOFT
lines` with the connected circuit. `IMU=FAULT` is expected because the sensor
cannot respond. If the lines rise in this test, the connected sensor or its
wires load the bus. If they remain low, the sensor is not the sole cause;
inspect the pull-up supply, MCU pin model and bus configuration next. This
comparison is a diagnostic experiment, not a working controller circuit.
Host tests do not reproduce the actual Wokwi peripheral model.

1. Download the new `downloads/FlightHapticController-project.zip` and extract it
   into a fresh directory to avoid running a stale firmware image.
2. Open that extracted folder in VS Code and run **Wokwi: Start Simulator**.
3. Copy the first five complete fault-record lines from the Wokwi terminal:
   `mode=...`, `HW ...`, `PINS ...`, `SOFT ...` and `CLOCK ...`.

Each fault record reports the following fields. Hardware fields preserve the
first failure before fallback changes the peripheral or pin configuration;
software fields describe the latest recovery and delay observations.

| Line | Meaning |
| --- | --- |
| `mode=...` | Mode, IMU validity/fault, register, identity, HAL result, current `err`, selected `bus` and retained original `hwerr`. |
| `HW` | `captured`, hardware error, last observed wait `flag`, and I2C `ISR`, `CR1`, `CR2`, `TIMINGR`. |
| `PINS` | GPIOB `IDR`, `MODER`, `OTYPER`, `PUPDR`, `AFRH` captured at that hardware failure; `BOOT` is `IDR` before the first transaction. |
| `SOFT` | Recovery result, timing-fault code, raw SCL/SDA levels before/after the latest recovery, GPIOB `ODR`, `MODER`, `PUPDR` afterward, and the separate-STOP read's `split` step and `serr` error. |
| `CLOCK` | SysTick `CTRL`, `LOAD`, first/last `VAL`, accumulated `cycles` and `polls` for the delay observation. |

Numeric software codes are declared in `Core/Inc/main.h`:

- `recover`: `0` OK, `1` NACK, `2` timeout, `3` bus-stuck result, `4` invalid
  argument. Read it alongside `timing`: a delay-clock failure can induce a
  recovery failure without proving that a slave holds the bus low.
- `timing`: `0` no detected fault, `1` SysTick disabled, `2` invalid configuration,
  `3` no observed counter progress, `4` millisecond guard, `5` polling guard.
- `lines`: bit 0 is raw SCL and bit 1 is raw SDA: `0` both low, `1` SCL high only,
  `2` SDA high only, `3` both high. The pair is before/after recovery, not proof
  that a transfer or slave ACK succeeded.

For a **pure hardware timeout** (`HW err=00000020`), the traced wait `flag` can
identify TXIS (`00000002`), RXNE (`00000004`), STOPF (`00000020`), TC (`00000040`)
or BUSY (`00008000`). These are flag masks, separate from the error code.
`flag=00000000` means no wait flag was traced; it does not identify the cause.
The supplied Makefile enables this read-only observer when compiling the HAL
I2C driver, and the prebuilt ZIP includes it. A custom build must retain that
driver-specific forced include to obtain the wait-flag trace.

Register access uses `HAL_I2C_Mem_Read/Write` with repeated START for reads.
A confirmed hardware timeout selects bounded open-drain GPIO I2C on PB8/PB9;
ordinary NACKs do not select it. Both paths require actual sensor ACKs, identity
and acceleration data. `IMU=OK ... bus=GPIO hwerr=0x00000020` would confirm
successful sampled data through fallback after the original timeout. This has
not yet been established in the reported Wokwi session.
